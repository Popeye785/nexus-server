## A/B-TEST-METHODE

### Methode 1 — SHADOW PARALLEL (empfohlen, sicher)

Alte Logik bleibt aktiv und entscheidet wirklich.
Neue Logik läuft parallel und wird nur protokolliert.

**Datenerfassung in neuer `shadow_test_runs`-Tabelle:**

```sql
CREATE TABLE shadow_test_runs (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  ts INTEGER NOT NULL,
  symbol TEXT NOT NULL,
  feature_name TEXT NOT NULL,        -- 'sharpe_softmax' | 'regime_aware_weights' | 'brain_voter'
  baseline_decision TEXT,            -- alte Logik
  shadow_decision TEXT,              -- neue Logik
  baseline_confidence REAL,
  shadow_confidence REAL,
  agreement INTEGER NOT NULL,        -- 1 oder 0
  outcome_pnl REAL,                  -- falls Trade ausgeführt: realisierter PnL (alte Logik)
  baseline_audit_id INTEGER,         -- FK zu consensus_decisions.id
  details_json TEXT                  -- alle Voter-States für späte Forensik
);
CREATE INDEX idx_shadow_feature_ts ON shadow_test_runs(feature_name, ts DESC);
```

**Auswertung nach 14-30 Tagen:**
- Wenn neue Logik in 60%+ der Fälle übereinstimmt: safe to activate
- Wenn neue Logik abweicht und Outcome positiv: Score++ (better)
- Wenn neue Logik abweicht und Outcome negativ: Score-- (worse)
- Aktivierung erst wenn `Better-Score > Worse-Score` über min 50 Decisions

### Methode 2 — SPLIT-SYMBOLS (mittel-sicher)

Symbol-Auswahl in zwei Gruppen:
- Gruppe A (alte Logik): BTC, ETH, SOL, NEAR, ADA
- Gruppe B (neue Logik): DOGE, BNB, ATOM, SUI, LINK

Nach 14-30 Tagen vergleichen:
- Performance pro Gruppe (Win-Rate, Profit-Factor, Sharpe, Max-DD)
- Statistical Significance via Welch's t-test

**Risiko:** Symbol-spezifische Faktoren verfälschen Vergleich (e.g. BTC/ETH dominanter als Altcoins).

### Methode 3 — TIME-SLICED (riskanter)

Tag 1-3: alte Logik | Tag 4-6: neue Logik | Tag 7-9: alte | usw.

Klare Vergleichbarkeit aber Markt-Phasen können verfälschen (Bull/Bear-Wechsel).

**Empfehlung: Methode 1 (Shadow Parallel)** — keine echten Trades mit ungeprüfter neuer Logik.

## METRIKEN ZUR AUSWERTUNG

| Metrik | Bedeutung | Zielwert für Aktivierung |
|---|---|---|
| Agreement-Rate | wie oft stimmen alt/neu überein | > 60% |
| Better-Score | wie oft wäre neu besser gewesen | > 50% von Disagreements |
| Worse-Score | wie oft wäre neu schlechter gewesen | < 40% von Disagreements |
| Confidence-Stabilität | Drift in conf-Werten | < 0.15 std über Sample |
| Regime-Coverage | wie viele Regimes durchlaufen | min 3 von 5 (BULL/BEAR/RANGING + 1) |
| Sample-Größe | min Decisions für stabile Aussage | min 200 |
| PnL-Spread (theoretisch) | PnL alte vs PnL neue (counterfactual) | neue > alte über Sample |

## RISIKEN UND CAVEATS

- **Marktregime-Bias:** Test-Zeitraum kann zufällig sein (z.B. nur RANGING). Backtest mit Reset-Day-Zero-Archive auch nötig für Cross-Validation.
- **Survivorship-Bias:** Wenn nur erfolgreiche Symbol-Pairs getestet werden, lernt die Logik Survivorship.
- **A/B-Test misst nur was wir messen** — übersehene Confounder bleiben (z.B. Liquidity, Bid-Ask-Spread).
- **Crypto-spezifisch:** Pump&Dump-Events können statistisch dominieren — Outlier-Filter empfohlen (z.B. trim top/bottom 5%).
- **Bei wenigen Trades pro Tag** (Bot ist konservativ): A/B-Test braucht lange. Mit n=4 Trades/Tag wären 200 Decisions = 50 Tage.
- **Voter-Performance-Data muss VOR Aktivierung gesammelt werden.** `recordVoterPnL`-Calls sind in `_executeTrade` einzubauen — aktuell NICHT der Fall. Empfehlung: separates `recordVoterPnL`-Hook in `Trades.close()` einbauen (wenn final PnL bekannt).
