## C.1 — WS-Race-Condition-Fix

**Wo:** `server.js:1294-1370` (Bitget.connectWS)

**Problem:** Bei simultanen `ws.on('close')` + `ws.on('error')` werden
2× `setTimeout(connectWS, ...)` schedult → exponential growth.

**Fix-Strategie:**
- Mutex/Lock auf `connectWS()` (z.B. `this._connectInFlight = true`)
- `close`-Handler dedupliziert: nur reconnect wenn nicht schon geplant
- Alten `this.ws` sauber-removeAllListeners() vor `terminate()`

**Test:**
```js
// scripts/test_ws_race.js
const ws = require('ws');
// Mock Bitget: simuliere terminate() + emit('error') parallel
// Erwartung: nur 1× connectWS-Aufruf in nächsten 5s
```

**DoD C.1:** Künstlicher Race-Test bringt nur EINE neue WS-Instanz.

**Vor Patch:**
```bash
cp server.js server.js.bak.WS_RACE_FIX_$(date +%Y%m%d_%H%M%S)
cp nexus.db nexus.db.bak.WS_RACE_FIX_$(date +%Y%m%d_%H%M%S)
```

**Nach Patch:**
- node --check
- Reproducer-Test laufen lassen
- PM2-Restart
- 30 Min Live-Beobachtung auf WS-Stability

**Aufwand:** ~30-45 Min, 1 PM2-Restart

## C.2 — Watchdog-Architektur umbauen

**Wo:** `server.js:18216+` (aktueller WSWatchdog v2)

**Problem:** Internes `setInterval` ist immun gegen Event-Loop-Block
(wenn Bot CPU-hungrig hängt, läuft `setInterval` auch nicht).

**Optionen:**
- **(a)** Cron + curl (außerhalb des Bot-Prozesses) — empfohlen
  ```cron
  */2 * * * * curl -s --max-time 5 http://localhost:3000/api/health > /dev/null || pm2 restart nexus
  ```
- **(b)** PM2-Health-Check mit `wait_ready` + Custom-Probe
- **(c)** Worker-Thread im Bot, unabhängig vom Main-Event-Loop

**Empfehlung:** (a) am robustesten weil komplett bot-extern.
(b) eleganter wenn PM2-Setup das gut unterstützt.

**Voraussetzung:** C.3 muss zuerst gemacht werden.

**DoD C.2:** Bot-Hang-Simulation (`while(true){}` injizieren) wird in
< 60s extern erkannt + restartet.

**Aufwand:** ~20 Min für Option (a), kein PM2-Restart nötig
(crontab-Edit reicht).

## C.3 — PM2 Health-Check-Hook

**Wo:** neuer Endpoint in `server.js`

**Anforderung:**
- Echter `/api/health`-Endpoint
- < 50ms Response, KEIN DB-Touch, KEIN Modul-State-Touch
- Antwortet nur wenn Event-Loop responsiv
- Format: `res.send('ok')` oder `res.json({ok:true, uptime:process.uptime()})`

**Code-Skelett:**
```js
app.get('/api/health', (req, res) => {
  res.set('Cache-Control', 'no-store');
  res.json({ ok: true, uptime: process.uptime(), pid: process.pid });
});
```

**PM2-Config (`ecosystem.config.js`):**
```js
{
  name: 'nexus',
  script: 'server.js',
  wait_ready: true,
  listen_timeout: 10000,
  // Optional: kill_timeout für sauberen Shutdown
}
```

**Frontend-Anpassung:** Polling auf realen Health-Endpoint umstellen
(aktuell wahrscheinlich `/api/v9/status` was es nicht gibt → HTTP 404
heute beim Verify-Test).

**DoD C.3:** PM2 zeigt `not-ready` wenn `/api/health` nicht antwortet
(via Bot-Hang-Simulation testbar).

**Aufwand:** ~15 Min, 1 PM2-Restart

## C.4 — Backtest-Throttling (vor nächstem F.2-Versuch)

**Problem heute 13.05.:** F.2-Backtest hat 175200 candles für BTC patterns
angefragt → ~875 API-Loops parallel zum Live-Bot-Cycle → Bitget-Druck
+ Event-Loop-Konkurrenz → mit WS-Race als Trigger Bot-Hang.

**Anforderung:**
- Backtest darf Live-Bot nicht in API-Konkurrenz drücken
- Backtest pausieren wenn WS-Connection unstable (`Bitget.wsReady === false`
  für >30s)
- Rate-Limit zwischen Batches (z.B. min 1000ms sleep zwischen Multi-Call-Iterationen)
- Optional: separater Worker-Thread für Backtest-Engine

**Wo:** `server.js:2540+` (TickBacktest.run) + `server.js:1099-1140`
(Bitget.fetchCandles Multi-Call-Loop)

**Code-Skelett:**
```js
// in TickBacktest.run pre-loop:
if (Bitget._lastWsErrorAt && Date.now() - Bitget._lastWsErrorAt < 30000) {
  return { error: 'WS unstable, backtest paused', wsHealth: Bitget.wsReady };
}

// in Multi-Call-Loop:
await new Promise(r => setTimeout(r, 1000));  // statt 200ms
```

**DoD C.4:** F.2-Backtest läuft, WS bleibt stabil, Bot bleibt responsiv
(HTTP-Health < 50ms während Backtest).

**Aufwand:** ~30 Min Code + 1 echter Test-Run
